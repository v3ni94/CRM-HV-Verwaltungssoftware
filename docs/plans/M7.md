# M7 KI-Gateway und Onboarding-Chat: plan and result

Status: backend and CRM screens done (2026-09-23). Source: MASTER-PROMPT 6.8, 9, 10,
18 (M7), rule 0.1.6 and 0.1.13.
Acceptance: an Excel contact list becomes contacts via chat; an owner and tenant list creates
property, units and contracts; undo works; evaluation set with at least 20 cases per task.

## Decisions

* Package `mhvp.ai`: `models` (ai_provider_config, ai_conversation, ai_message, ai_task_run,
  ai_proposal, ai_example, import_run, import_run_item; migration 0007 with RLS), `tasks`
  (strict output schemas, prompt registry `prompts/<task>/v<n>.md`), `providers` (protocol,
  Anthropic adapter via the official SDK with `output_config.format` json_schema and a cached
  system prompt), `gateway` (checks, input preparation, cost, dedup, validation with one retry),
  `imports` (preview, apply, undo), `jobs` (Celery task `mhvp.ai.run`), `routers`, `evaluate`.
* Before any data leaves the platform (A-019): released provider (four eyes, change withdraws
  the release), DPA evidence, training opt-out, key, prices, budget above 0 and not reached.
  Blocked runs are recorded with the reason and no provider call.
* Tiers per task (9.3): extraction `large`, questions and summaries `small`; model names and
  prices come from the tenant configuration, not from code.
* Input preparation is deterministic: Excel and CSV to numbered rows, text layer of documents;
  scans without text are refused; oversized input is refused, never truncated silently.
  Document content is wrapped in `<daten>`; every prompt forbids following instructions from it.
* Outputs are validated against the schema; invalid values from the model (phone, e-mail, IBAN,
  amounts, areas) are dropped with a note in the preview, never repaired.
* Proposals: contacts with traffic light (new, existing with duplicate score, incomplete,
  invalid); property as tree with notes and questions. Nothing is created before confirmation;
  apply runs in one transaction and records every entity in `import_run`. Undo removes in
  reverse order what is not bound (documents linked, contracts changed, deposits, mandates,
  owners) and reports kept items with the reason (A-020).
* `answer_question` uses full text retrieval over the tenant's documents until embeddings are
  decided (M7-03); requires `documents:read`.
* Learning examples are not stored yet (M7-04); OpenAI adapter and provider fallback are open
  (M7-02).
* Evaluation: 87 synthetic, anonymised cases in `apps/api/tests/ai_eval/` (24 contacts, 22
  properties, 21 questions, 20 summaries) with recorded answers; `make ai-eval` and CI compute
  field F1 of the post-processing against independent expectations (threshold 0.95). This does
  not measure model quality (M7-05).
* Permissions: resource `ai` (standard staff read, create, delete for undo); provider setup
  needs `tenant_settings:update`, release `ai:approve` by another person. Chats are personal.
* `MHVP_AI_INLINE` runs tasks in the request for development and tests; refused in staging and
  prod.

## M7-06 fast table import (operator 25.09.2026, result 25.09.2026)

Problem: CSV/XLSX imports through the AI chat sent every row through the LLM (864 rows = 11
chunks, 30 to 60 seconds each). `docs/rules/M7-06.md` has the full rule; summary here.

* New task `map_columns` (tier `small`): header plus up to 5 sample rows, returns a column to
  field mapping with confidence. `mhvp.ai.table_mapper` then processes every row deterministically
  in Python (name split incl. salutation/title, company detection, address split, postal
  code/city split, phone/e-mail lists, IBAN passthrough, role); only rows it cannot read with
  confidence (two persons in one cell, no readable name) become `residual` and still go through
  the existing row-chunked `extract_contacts` LLM extraction, now shared as `gateway._process_chunks`
  between the old and the fast path. Merge keeps `source_row` and the `ContactsResult` shape, so
  `contacts_preview`/`apply` and the chat UI are unchanged. Only `extract_contacts` on a single
  CSV/XLSX document is covered; `extract_property` stays on the row-chunked path (open point,
  M7-06, its rows carry unit/party/payment structure the mapper does not model).
* Feature flag `TenantSettings.ai_fast_table_import` (default on), `GET`/`PUT
  /api/v1/ai/fast-table-import` (`tenant_settings:update`). Falls back to the full chunked LLM
  path per run when the mapping's confidence is below 0.6 or no header is detected, or when no
  provider route is available for `map_columns`.
* Progress stages: "Spalten erkannt", "n Zeilen verarbeitet", "m Zeilen an KI" (only with
  residual rows), "Fertig". The chat widget's progress indicator only shows a generic
  uploading/queued/processing/done state (`AiChatWidget.tsx`), not the backend's free text
  stage, so no frontend change or Vitest update was needed.
* Migration `0067_ai_fast_table_import`: `ai_task` enum value `map_columns`,
  `tenant_settings.ai_fast_table_import` (boolean, default true).
* Tests: `apps/api/tests/unit/test_m7_fast_table_import.py` (14 cases: name split incl. "Herr
  Dr. Hans Müller", "Müller GmbH", "Hans und Erika Müller" → residual, empty cells, address
  split "Hauptstr. 12a", cp1252 umlauts); `apps/api/tests/integration/test_m7_ai.py::test_fast_table_import_only_sends_residual_rows_to_the_provider`
  (measured speedup: a 50 row CSV with 2 ambiguous rows made 2 provider calls total — 1
  `map_columns` plus 1 call for the 2 residual rows — instead of 1 call per chunk of up to 80
  rows for all 50 rows; for the operator's 864 row case this turns roughly 11 chunk calls into 1
  map_columns call plus at most a handful of residual-row calls, provided most rows map cleanly)
  and `::test_fast_table_import_falls_back_on_low_confidence_mapping` (low confidence: falls
  back to the full chunked path, 1 map_columns call plus 1 full-table call, `run["model"]` is
  the large tier extract_contacts model). The two pre-existing chunked-path tests
  (`test_contact_list_to_contacts_and_undo`, `test_large_spreadsheet_is_chunked_not_blocked`)
  now call `PUT /api/v1/ai/fast-table-import {"enabled": false}` first so they keep testing the
  old path unchanged.
* Gates run: `ruff check`/`format`, `mypy src/mhvp/ai` (strict, no issues), the full
  `tests/integration/test_m7_ai.py` + `tests/unit/test_m7_ai.py` +
  `tests/unit/test_m7_fast_table_import.py` (38 passed, twice in a row for flakiness).
* Not executed: `apps/web-crm` tsc/eslint/vitest (no frontend file changed by this task, so not
  re-run); `alembic upgrade head` against the shared dev database (blocked after 3 retries by an
  unrelated concurrent migration `0069_tenant_billing_settings` on another agent's work; the
  fresh test database used by pytest applies all migrations including `0067` without issue).
