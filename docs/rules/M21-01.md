## Regeln

- Der Anmeldelink ist 15 Minuten gültig und wird nach der ersten Einlösung sofort gesperrt
  (`used_at`); eine zweite Einlösung desselben Links scheitert mit `MHVP-AUTH-0011`. Nur der
  SHA-256-Hash des Linkgeheimnisses wird gespeichert, nie der Link selbst; keine Antwort der
  API enthält Link oder Code (Abschnitt 0.1.13).
- Die Anfrage nach einem Anmeldelink (`POST /magic-link/request`) beantwortet jede Adresse
  identisch (Status 204), unabhängig davon, ob ein Portalkonto besteht: keine Preisgabe der
  Kontoexistenz. Je Adresse und Stunde werden höchstens fünf Anfragen angenommen
  (`magic_link.RATE_LIMIT_PER_HOUR`), weitere Anfragen im selben Fenster werden verworfen,
  ohne dass sich die Antwort ändert.
- Der optionale zweite Faktor per E-Mail-Code (`portal_account.magic_link_2fa`, Standard aus)
  wird ausschließlich durch die Verwaltung je Konto eingeschaltet (`contacts:update`), nie
  vom Portalkonto selbst; er ist nie verpflichtend. Ist er aktiv, ersetzt der eingelöste Link
  keine Sitzung, sondern liefert eine Codeanforderung; der sechsstellige Code ist zehn Minuten
  gültig, einmal nutzbar und wird getrennt per E-Mail versendet.
- Die bestehende Passwortanmeldung (`POST /auth/login`) bleibt unverändert nutzbar; der
  Magic-Link ist ein zusätzlicher, kein ersetzender Weg. Eine erfolgreiche Einlösung stellt die
  Sitzung über denselben Mechanismus aus wie die Passwortanmeldung
  (`mhvp.core.auth.service.issue_session`): gleiche Zugriffstoken, gleiche Aktualisierungstoken,
  gleiche Mandantenwahl.
- Die QR-Einladung für den postalischen Brief nutzt denselben Mechanismus wie die bestehende
  Konto-Erstaktivierung (`invitation_hash`/`invitation_expires_at`), jedoch mit einer auf 90 Tage
  verlängerten Gültigkeit (`QR_INVITE_DAYS`), weil ein Brief die Empfängerin oder den Empfänger
  erst mit Verzögerung erreicht. Das Anfordern eines neuen Briefs (POST, nicht GET) ersetzt einen
  zuvor ausgegebenen Code; ein bereits verschickter Brief mit dem alten Code wird damit
  ungültig, das ist beabsichtigt (kein Vorababruf ohne Wirkung).
- Mandantentrennung: der Link kodiert den Mandanten im Klartextteil des Tokens
  (`<mandant_hex>.<geheimnis>`, wie die bestehende Einladung); die Suche nach dem Hash erfolgt
  ausschließlich innerhalb dieses Mandanten (RLS, ADR 0002). Ein verändertes Mandantenkürzel
  im Token findet keine fremde Zeile, sondern scheitert mit `MHVP-AUTH-0011`.
- Fehlschläge beim Mailversand (kein eingerichtetes Postfach, `mhvp.sla.channels.send_email`)
  werden protokolliert, ohne Token oder Code im Log, und ändern die Antwort der Anfrage nicht
  (weiterhin 204); der Link oder Code existiert dann serverseitig, erreicht aber niemanden.
