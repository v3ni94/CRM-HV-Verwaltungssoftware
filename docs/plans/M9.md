# M9 Oberfläche und Betrieb: plan and result

Status: done in the repository (2026-09-23); server rollout open (M9-01, M9-02).
Source: MASTER-PROMPT 3.5, 6.9.5, 16, 17, 18 (M9).
Acceptance: HVM works in parallel with Immoware24 on master data in the platform; backup
restore tested. The restore test passes locally and in CI; the parallel operation needs the
real import (M8-01) and the server (M9-01), see M9-05.

## Decisions

* Package `mhvp.workspace`: `models` (notification, calendar_entry, saved_filter; migration
  0009 with RLS), `services` (idempotent `notify`, derived calendar dates, maintenance
  reminders), `routers` (`/api/v1/workspace`), `tasks` (Celery `mhvp.workspace.reminders`,
  hourly beat), `ops` (`/api/v1/platform/ops/metrics`, platform admins only).
* Dashboard tiles follow the caller's permissions; no money figures until G1
  (`accounting: locked_until_g1`). Upcoming dates cover the last 30 and next 30 days.
* Global search over contacts, properties, units, contracts and documents, each part only
  with the matching read permission; RLS keeps tenants apart.
* Calendar: own and shared appointments plus derived maintenance and contract dates; derived
  dates are computed on read, never copied (no second source of truth).
* Bulk actions: contact tags and maintenance done only; all or nothing, permission checked,
  recorded as domain event. No bulk action with money effect exists (gates G1 to G5).
* Dark mode: system default, manual override per browser (`data-theme`), tokens stay neutral.
* Operations: `scripts/backup.sh` (pg_dump, age encryption mandatory unless explicitly
  allowed for tests, sha256, 30 days rolling), `scripts/backup-verify.sh` (restore into a
  throwaway database, revision and table checks), `scripts/deploy.sh` (`make deploy
  ENV=staging|prod`, backup before production migration, explicit tag confirmation for prod).
* Monitoring: counts per job (webhooks, DMS mirror, AI runs, notifications) as JSON with
  alert list and as Prometheus text.

## Result

* API tests: `tests/integration/test_m9_workspace.py` (dashboard by permission, search by
  permission and tenant, reminder idempotency, calendar visibility and ownership, filters per
  user, bulk all or nothing and permission, ops metrics admin only).
* Backup and restore: CI step "Backup and restore test (M9)" and local run.
* CRM: `/start`, `/kalender`, notification menu, theme switch, search over all areas, saved
  filters and bulk tagging in the contact list; Vitest in `Workspace.test.tsx`.
* Not executed: `make deploy` against a server (no server data, M9-01); age encryption path
  (tool not installed locally; unencrypted path used for the test with explicit opt in).

## Addendum 26.09.2026: daily jobs of section 15.1 (A40, A41)

Rule `docs/rules/M9-06-tagesjobs.md`. Added to `mhvp.workspace`: `jobs.py` (digest per user,
deadline list per tenant), tasks `mhvp.workspace.digest` (beat 07:00 Europe/Berlin) and
`mhvp.workspace.compliance_deadlines` (beat 20:00), tables `workspace_job_settings`
(`digest_mail_enabled` default off, `deadline_lead_days` default 30), `digest_run`
(one row per tenant, user and day) and `compliance_deadline` (migration `0101_workspace_jobs`,

default. Deadline sources: contract end and termination dates, meter calibration dates
(`meter.calibration_due_date`), bank consent (`finapi_connection` before `bank_connection`),
document retention end, notice date of service provider contracts (`service_contract`,
M9-06, fixed lead time 14 days, plan `docs/plans/M9-06-dienstleistervertraege.md`) and the
resolution deadline of virtual meetings (entered field with source, fixed lead time 7 days,
M9-07, since 26.09.2026). Both sources exist since 26.09.2026; the earlier "not covered" notes
for M9-06 and M9-07 are superseded.

Tests: `tests/integration/test_m9_jobs.py`, `tests/unit/test_worker.py` (beat entries as a
subset check because A29 and A38 add entries in parallel), Vitest `DigestCard.test.tsx` and
`DeadlinesTable.test.tsx`. Not executed: a real mail send (no mailbox in the test database).
`make openapi` (client regeneration) is left to the integrator because `openapi.json` is
shared between parallel tasks; the CRM pages use `serverFetch` for the new endpoints.

## Addendum 26.09.2026: rule engine stage 1 (A38)

Package `mhvp.automation` implemented (section 15.2, rule document `docs/rules/M9-02-automation.md`):

* Tables `automation_rule`, `automation_run`, `automation_watermark` (migration 0100, tenant
  RLS). Conditions as a JSON tree (`and`/`or`, `eq`/`ne`/`contains`/`gt`/`lt`) over event
  fields and the current ticket fields; actions limited to create ticket from template,
  internal notification (users, roles) and set ticket field (priority, team, category,
  assignee). No posting, payment, approval or external sending (rules 0.1.6, 0.1.7).
* Beat job `mhvp.automation.process_events` every minute with a watermark per tenant over
  `domain_event`; the event system is unchanged. One run per rule and event, savepoint per
  rule, depth 1 loop guard via the `automation` payload marker.
* API `/api/v1/automation/{meta,rules,runs}` with activate and dry run; CRM page
  `Einstellungen, Automatisierung` (list, form with condition rows and actions, test run, log).
* Tests: `tests/unit/test_automation_rules.py`, `tests/integration/test_m9_automation.py`,
  `AutomationAdmin.test.tsx`. Not executed: the Celery beat itself against a broker (the
  task body `process_events_once` is covered by the integration test).
* Open: a `ticket.updated` event in the ticket domain for field change rules. Stage 2 (A39) is
  implemented, see the next addendum.

## Addendum 26.09.2026: rule engine stage 2 (A39)

Stage 2 of `mhvp.automation` (rule document `docs/rules/M9-02-automation.md`):

* Actions `webhook` (signed per rule, secret encrypted with the tenant scope and never
  returned, https only, private targets only with `webhook_allow_private_targets`, one
  attempt per run), `mail_draft` (draft in the ticket mailbox from a ticket reply template,
  four eyes untouched, never sent), `letter_draft` (letter from a document template on the
  letterhead, stored as a generated document linked to contact, property, unit and ticket),
  `ai_task` (queued gateway run for summarize, draft_reply, answer_question,
  classify_email; proposal only). No posting, payment, approval, IBAN or send action.
* Trigger kind `schedule` (daily, weekly, monthly at a time in Europe/Berlin): the existing
  beat task runs due rules once per due moment (`last_scheduled_at` per rule plus a
  deterministic run id per rule and window). Migration 0110 (`trigger_kind`, `schedule`,
  `last_scheduled_at`, `trigger_event_type` nullable); no new tenant table, RLS unchanged.
* CRM form rebuilt: trigger kind, event type select, schedule editor, condition rows with
  select fields (category, priority, team, ...), editors for all seven actions, rule sentence
  preview ("Wenn Ticket angelegt mit Ticket Kategorie gleich Wasserschaden, dann Priorität
  Hoch, Team Objektbetreuung."), JSON expert view for nested conditions.
* Tests: `tests/unit/test_automation_schedule.py`, `tests/integration/test_m9_automation_stage2.py`
  (local HTTP receiver verifies the signature), `AutomationAdmin.test.tsx` (7 cases). Not
  executed: the Celery beat against a broker, a real AI provider call (the run is only
  queued), a real mail send (none exists by design).
* Open: retry plan for rule webhooks (M9-08), AI runs in `ai_inline` mode stay queued
  (M9-09), conditions on data beyond the ticket.
