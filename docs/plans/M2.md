# M2 Plattform und Mandanten: plan

Status: in progress (2026-09-23). Source: MASTER-PROMPT 3.3, 3.4, 3.5, 5, 6.8, 6.9.9, 12, 18 (M2).
Acceptance (section 18): two tenants (HVM, Timo Müller) from seeds with CI values; user switch

## Scope and decisions

| Area | Implementation |
| --- | --- |
| Platform tables (no RLS, 5.3) | `tenant`, `tenant_domain`, `app_user`, `membership`, `refresh_token`, `oidc_client`, `oidc_authorization_code`. `membership` is platform level because login must list a user's tenants before a tenant context exists (ADR 0006). The RLS guard test carries this allowlist explicitly. |
| Tenant tables (RLS) | `role`, `role_permission`, `membership_role`, `tenant_settings`, `api_key`, `release_gate_request`, `domain_event`, `audit_log`, `webhook_subscription`, `webhook_delivery`. |
| Passwords | Argon2id (argon2-cffi defaults). Length 12 to 128, no composition rules, lockout after 10 failures for 15 minutes (ASSUMPTIONS A-012). |
| 2FA | TOTP (RFC 6238, pyotp) mandatory for every CRM login (3.4: "Pflicht für Verwaltungsrollen"). Secret encrypted. |
| Tokens | Access JWT ES256, 15 min, claims `sub`, `tenant_id`, `roles`, `scopes`, `platform`; refresh tokens opaque, stored as SHA-256, rotating per family, reuse revokes the family; session list and revoke. |
| API keys | `mhvp_<prefix>_<secret>`, SHA-256 stored, scopes, expiry, last use, revoke. |
| OIDC provider | discovery, JWKS, authorize (code + PKCE S256 only), token, userinfo for registered clients. Login UI for the browser redirect follows with the CRM UI (M9); M2 authorize accepts an authenticated bearer. |
| Permissions | resource x action (`read`, `create`, `update`, `delete`, `approve`, `export`), roles per tenant with inheritance; system roles from annex A.4 seeded. M2 resources: `tenant_settings`, `members`, `roles`, `api_keys`, `webhooks`, `audit`, `release_gates`. |
| Tenant resolution | Host header against `tenant_domain`; token tenant must match (3.3). Platform admin switch is explicit, requires a reason and is recorded as event in the target tenant. |
| Encryption | `EncryptedText` with AES-256-GCM, key per scope derived by HKDF from `MHVP_MASTER_KEY` (tenant id or `platform`), scope bound as AAD and checked on decrypt (3.5). |
| Events, audit | `domain_event` and `audit_log` append-only (trigger rejects UPDATE/DELETE). Events are the outbox for webhooks. |
| Webhooks | subscriptions per tenant, HMAC-SHA256 `X-MHVP-Signature: t=<unix>,v1=<hex>` over `<t>.<body>`, retries 1 min, 5 min, 30 min, 2 h, 6 h, 24 h, manual redelivery, SSRF guard (no private targets outside dev/test), no redirects. |
| Release gates | `release_gate_request`: tenant admin requests with scope and evidence reference, a platform admin who is a different person approves; revocable; `DbReleaseGateResolver` replaces the closed default. No gate is opened by seeds. |
| Seeds | `mhvp/tenant/seeds/*.json` from skills `hvm-ci` and `ci-timo-mueller-einzelunternehmen`; missing values `TODO`; `make seed`. V14 release stays open. |

Out of scope: UI for login and administration (M9), SSO clients of existing tools (after V1).

## Nachtrag (2026-09-25): Löschrecht nur Administrator (docs/rules/M2-07.md)

Betreiberanforderung 25.09.2026: kein Mitarbeiter darf Datensätze löschen; nur `tenant_admin`
(und der Plattformadministrator nach Mandantenwechsel) halten `*:delete`. Umgesetzt:

* `mhvp.core.auth.permissions`: `_TICKETS` und `_MASTER_RWD` vergeben kein `delete` mehr; damit
  verlieren die Systemrollen `standard`, `clerk_no_accounting` und `technical_clerk` ihr
  Löschrecht auf `contacts`, `properties`, `contracts`, `documents`, `ai` und `tickets`.
  Unveränderte Rollentabelle im Übrigen. Test `tests/unit/test_permissions_delete.py` sichert
  die Regel dauerhaft ab (nur `tenant_admin`/`administrator` mit `*:delete`).
* Bestehende API-Tests (`test_m3_contacts.py`, `test_m2_platform.py`) laufen unverändert grün;
  sie erwarteten bereits 403 für nicht administrative Rollen beim Löschen beziehungsweise
  nutzten für erlaubte Löschungen die Rolle `admin`, keine Anpassung nötig.
* CRM UI: `ContactActions` blendet die Löschen-Schaltfläche aus, wenn `contacts:delete` in
  `GET /api/v1/auth/me`.`permissions` fehlt (`apps/web-crm/src/app/(app)/kontakte/[id]/page.tsx`
  reicht `canDelete` durch). Vitest `ContactActions.test.tsx` deckt beide Fälle ab.
* Offen (siehe `docs/OPEN_QUESTIONS.md`): dieselbe UI-Gate ist bislang nur für Kontakte
  umgesetzt; Tickets, Dokumente, Objekte, Angebote, Übergabeprotokolle und Wissensdatenbank
  zeigen aktuell keine eigenen Löschen-Schaltflächen im CRM (kein UI-Bestand zum Gaten
  gefunden) und sind bei Einführung nach demselben Muster zu sichern.

## Nachtrag (2026-09-25): Verwalter-Kontakt und Portalzugang je Mitarbeiter (M2-08 entschieden)

Integrator-Entscheidung 25.09.2026 (M2-08, `docs/OPEN_QUESTIONS.md`): jeder Mitarbeiter erhält
bei Anlage automatisch einen CRM-Kontakt mit Kontaktrolle "Verwalter" und einen mandantenweiten
Portalzugang mit Rechten je CRM-Rolle. Umgesetzt:

* Migration 0056 (`portal_role_permissions` auf `tenant_settings`, JSONB, Überschreibungen der
  eingebauten Grundeinstellung); die Verknüpfung Mitgliedschaft/Kontakt nutzt das bereits aus
  Migration 0033 vorhandene `membership.contact_id`, keine neue Spalte nötig.
* `mhvp.platform.routers.ensure_manager_contact_and_portal_access` (aufgerufen aus
  `invite_member`, dem einzigen Pfad, der Mitgliedschaften anlegt: `add_member` deckt sowohl
  Neuanlage als auch Wiedereinladung ab): sucht zuerst einen Kontakt mit derselben E-Mail im
  Mandanten (Wiederverwendung), legt sonst einen neuen an, setzt die Kontaktrolle `verwalter`
  und ruft `ensure_staff_portal_access` auf.
* `mhvp.portal.staff_access`: Katalog der Portalrechte
  (`documents:read`, `tickets:read`, `tickets:create`, `tickets:comment`, `work_orders:read`,
  `handover:read`), Grundeinstellung je Systemrolle (Administratoren alle, die meisten
  operativen Rollen Lesen plus Ticket anlegen/kommentieren, Support nur Lesen), Katalog der
  ausgenommenen Rollen (`portal_user`, `read_only`, `read_only_master_data`, `tax_advisor`,
  `insurance_broker`).
* `mhvp.portal.access`: neuer `legal_basis = "staff_access"` in `MANUAL_BASES` (übersteht einen
  Resync aus Vertragsdaten unverändert), `staff_permissions()` liest die Rollen der
  Mitgliedschaft und die Mandantenkonfiguration zusammen; `visible_documents` liefert für Staff
  mit `documents:read` alle Dokumente des Mandanten statt nur verlinkte. Portal-Endpunkte
  `GET /portal/tickets` und `GET /portal/work-orders` zeigen für Staff mit den passenden
  Rechten alle Tickets beziehungsweise Arbeitsaufträge des Mandanten.
* Neue Endpunkte `GET`/`PUT /api/v1/tenant/portal-role-permissions` (Lesen: `tenant_settings:read`,
  Ändern: `tenant_settings:update`) und `POST /api/v1/tenant/portal-role-permissions/resync`
  (wendet die aktuelle Matrix auf alle bestehenden Staff-Zugänge an, lässt externe
  Portalnutzer unberührt).
* CRM: `Einstellungen/Rollen` zeigt unter "Portalrechte je Rolle" eine Checkbox-Matrix
  (`PortalRolePermissions.tsx`), editierbar nur mit `tenant_settings:update`.
* Tests: `tests/integration/test_m2_platform.py`
  (`test_new_member_gets_manager_contact_and_portal_access_idempotently`,
  `test_portal_role_permissions_matrix_and_resync`),
  `tests/integration/test_m21_portal.py::test_staff_portal_sees_tenant_wide_data_per_matrix`;
  Vitest `PortalRolePermissions.test.tsx`.
* Nachtrag 26.09.2026 (Restpunkt M2-08 erledigt): eigener lesender Portal-Endpunkt für
  Mitarbeiter `GET /api/v1/portal/handovers` (Liste, Filter `property_id`, `status`) und

## Nachtrag (2026-09-26): Idempotenz und Ratenbegrenzung (A48, A49, ADR 0008)

Umgesetzt als reine ASGI-Middlewares in `mhvp.core`, Speicher Redis mit TTL, keine Migration:

* `mhvp.core.idempotency.IdempotencyMiddleware`: Header `Idempotency-Key` auf POST, PUT,
  PATCH, DELETE; Schlüssel je Mandant und Benutzer beziehungsweise API-Key; erste Ausführung
  sperrt den Datensatz (`SET NX`, 24 Stunden); gleicher Schlüssel mit anderem Aufruf 422
  `MHVP-CORE-0007`, laufende Erstausführung 409 `MHVP-CORE-0008`, Wiederholung liefert
  Status, Content-Type und Body mit `Idempotent-Replayed: true`; ungültiger Schlüssel 422
  `MHVP-CORE-0009`. Ohne Header bleibt alles wie bisher, die eigene Idempotenz von
  Buchungen, Umlagen und Abrechnungen bleibt unverändert.
* `mhvp.core.ratelimit.RateLimitMiddleware`: festes Fenster je Minute mit Redis-Zähler,
  Grenzen aus Settings (`MHVP_RATE_LIMIT_PER_MINUTE_USER` 600 je Mandant und Nutzer oder
  API-Key, `MHVP_RATE_LIMIT_PER_MINUTE_ANONYMOUS` 120 je Client-Adresse für unauthentifizierte
  Aufrufe wie Login, MFA, eingehende Webhooks; Konfiguration, keine Rechtsregel). Header
  `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` auf jeder Antwort,
  bei Überschreitung 429 `MHVP-CORE-0006` mit `Retry-After`; `/api/v1/health/*` ausgenommen;
  bei nicht erreichbarem Redis wird durchgelassen und gewarnt (Traefik hält das Edge-Limit).
* `mhvp.core.request_identity`: Identität für Middlewares aus Bearer-Token (Signatur geprüft)
  oder API-Key (nur geparst, Geheimnis prüft weiterhin die Auth-Abhängigkeit).
* Reihenfolge in `mhvp.main`: Correlation-ID (außen), Ratenbegrenzung, Idempotenz, Router.
* Tests: `tests/integration/test_m2_idempotency_ratelimit.py` (Wiederholung ohne zweite
  Wirkung, abweichender Body 422, laufende Erstausführung 409, Mandanten- und
  Nutzertrennung, gespeicherte 4xx-Antwort, Header und Health-Ausnahme, 429 mit niedriger
  Grenze über Settings-Override).
* Offen: Sliding Window und Budgets je Endpunkt; gespeicherte Antwort enthält nur
  Content-Type (kein `Location`); Nachweis im Mehrprozessbetrieb (gemeinsames Redis) nur
  rechnerisch, nicht gemessen.
