# M14 Belegeingang und Kreditoren: plan and result

Status: invoice core implemented 2026-09-23; AI extraction (extract_invoice) as proposal, mail
attachment and Paperless intake, and the CRM review form implemented 2026-09-25. Automatic intake
(`invoice_intake_auto`, default off) implemented 2026-09-26, activation by the operator open, see
M14-05. Source: MASTER-PROMPT 6.4, 6.9.9, 7.3, 7.9.1, 18
(M14).
Acceptance: PÜ01 to PÜ05; original, payment and order reference, change effects, cash
discount, partial and final invoice and changed IBAN tested; no payment from board status.

## Decisions

* `mhvp.accounting.invoices`, migration 0014: invoice (review status and posting status
  separate, payment hash of release, encrypted payee IBAN, deductions for final invoices,
  supersedes, duplicate hint, findings), invoice_line, invoice_review (PÜ05 per step and
  version), recurring_invoice_plan.
* Automatic checks write findings only (missing original, arithmetic, duplicates, IBAN not in
  master data). Review status is the aggregate of recorded human steps of the current version.
* Release by a second person, bound to a hash of amount, payee, IBAN, due date, number, ledger
  and deductions; any change voids it. A changed IBAN needs a separate confirmation by another
  person before release.
* Posting: expense lines against a creditor account (070000 ff., created per provider), payable
  open item; final invoices post only the remaining effect (D12).
* No payment here; payment release and execution are M15 and G2. There is no board status that
  could trigger a payment.

* AI extraction (2026-09-25): new task `extract_invoice` (`mhvp.ai.tasks.InvoiceExtractionResult`,
  prompt `mhvp.ai.prompts.extract_invoice.v1`), started like every other extraction task through
  the existing chat endpoint (`POST /ai/conversations/{id}/messages`, `task=extract_invoice`,
  `document_ids`); reuses the gateway's tier escalation, budget and release checks as is, no
  dedicated intake endpoint was needed for this path. The run produces an `AiProposal`
  (`entity_type=invoice`) with the header fields, a name based supplier candidate search
  (`mhvp.ai.imports.invoice_preview`) and platform side warnings for a duplicate invoice number
  and an IBAN that differs from the known bank accounts of a uniquely identified supplier; these
  checks are computed from tenant data, never invented by the model (rule 0.1.6). `GET
  /ai/proposals/{id}` masks the IBAN to its last four digits; the full value never reaches the
  reviewer from the AI side, they confirm the IBAN themselves in the review form from the
  original document. `POST /ai/proposals/{id}/apply` takes a complete, human confirmed
  `InvoiceApplyIn` (ledger, provider contact, header fields, document link, lines with ledger
  accounts) and creates the invoice through the existing `mhvp.accounting.invoices.write` path,
  so it starts in review status `open` (draft) with `posting_status=unposted`; the existing
  `evaluate()` findings (missing original, duplicate number, unconfirmed IBAN, arithmetic) apply
  unchanged and still require the four eyes review and release before posting. No new migration
  was needed; `extract_invoice` already existed in `AiTask` and no new table or column was added.
* Intake (2026-09-25): a mail attachment action, `POST /mail/messages/{message_id}/attachments/
  {attachment_id}/invoice-extraction` (`accounting:create`, rejects a non-PDF or an attachment not
  on that message, starts `extract_invoice` in a fresh conversation of the acting user, context
  `invoice`/`message_id`), and a Paperless pull, `POST /invoices/intake/paperless` (same
  permission, body `{paperless_document_id}`), reusing the read only `PaperlessSearch` client
  already used for the ticket/property DMS panels (M31) to fetch the file and
  `mhvp.documents.services.store_document` (source `import`) to index it, then the same
  extraction start. Both share a new `mhvp.ai.routers.start_extraction_run` helper factored out of
  the chat message endpoint, so tier escalation, budget and release checks stay identical to every
  other extraction path. Automatic intake behind the tenant switch
  `invoice_intake_auto` (default off) was added 2026-09-26, see below.
* Currency (2026-09-25): `InvoiceApplyIn.currency` (default EUR) is checked in
  `mhvp.ai.imports.apply_invoice`; anything other than EUR is rejected with a German message and
  nothing is created (rule 0.1.3, do not silently create), and `invoice_preview` already surfaces
  a "Fremdwährung erkannt" warning on the proposal before the reviewer gets that far. The `Invoice`
  model itself still has no currency column; the platform assumes EUR throughout (rule 9), so a
  non EUR invoice needs its own decision before any support beyond this hard block is added.
* CRM UI (2026-09-25): "Aus Dokument erfassen" under Rechnungseingang
  (`components/invoices/InvoiceExtract.tsx`), polling the run like `AiChatWidget`, then a review
  form with every extracted field editable, the IBAN shown masked (read only) next to a required
  "IBAN aus dem Original eintragen" field that is never pre-filled from the proposal, supplier
  candidate and ledger/account selection as in the manual invoice form, and "Als Entwurf anlegen"
  posting the apply. The same component, given a proposal id, renders directly in review stage
  (`/rechnungen?proposal=<id>`). In `MailDetail`, each inbound attachment gets a "Als Rechnung
  erfassen" action that calls the mail endpoint and then links to that review. A non EUR proposal
  disables the submit button with the German blocking message client side too.

* Automatic intake (M14-05, 2026-09-26, default off): tenant switch
  `tenant_settings.invoice_intake_auto` (migration 0086, down_revision 0083, `server_default`
  false), `GET/PUT /ai/invoice-intake-auto` (`tenant_settings:update`, event
  `invoice_intake_auto.updated`) and a switch with an AI cost hint under Einstellungen, DMS
  (`components/invoices/InvoiceIntakeAutoSettings.tsx`). With the switch on, the Celery Gmail
  sync (`mhvp.communication.tasks.gmail_sync_all_once`) collects the ids of newly created
  messages per mailbox and `mhvp.communication.invoice_intake.intake_for_messages` creates one
  queued `extract_invoice` run per matching attachment through
  `mhvp.ai.routers.create_extraction_run`, the session level core that `start_extraction_run`
  now also uses; the runs are dispatched after commit to the existing `mhvp.ai.run` task, so
  tier escalation, budget and release checks of the gateway are unchanged. The run is a system
  action: conversation and run belong to the mailbox creator, `input_ref.trigger` is
  `invoice_intake_auto`. The result stays a proposal for review; nothing is posted. Heuristic
  (no AI): inbound message, PDF attachment, and subject contains Rechnung, Invoice or Beleg, or
  the sender local part contains rechnung, invoice or billing, or the file name contains
  Rechnung or Invoice (case insensitive) or an uppercase `RE-` at the start or after a
  separator. Idempotency: table `invoice_intake_auto_run` (RLS, unique `tenant_id,
  document_id`) claimed per attachment with `INSERT ... ON CONFLICT DO NOTHING`; only the claimer
  creates a run, so a repeated sync, a retry or a parallel worker never starts a second run. A
  failure in the intake runs in its own savepoint and never rolls back the mail sync. The manual
  sync endpoint (`POST /mail/mailboxes/{id}/sync`) does not trigger the automatic intake.
