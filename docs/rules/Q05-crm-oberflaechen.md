| Scope | web-crm: `ContactParties` (`PartiesPanel`), `ContactTagsAdmin` (page `/einstellungen/kontakt-tags`), `TeamsAdmin` (page `/einstellungen/teams`), `VatOptionHistory` (unit page), `PropertyGallery` and `OccupancyList` (property page), `PortalRepresentationsPanel` and `PortalStatusBadge` (contact page), `TicketLocationFields`, `TicketForms` (create and edit), `TicketBulkAssign` (ticket list). API: `GET /portal-admin/representations` additionally returns `representative_contact_id` and `representative_email`. No migration, no new endpoint |
| Source status | Fachliche Umsetzung (6.1 party, party_member, contact_tag, portal_account; 6.2 unit_vat_option, property.images; 6.6 team, ticket; milestone M5 occupancy list; M21 power of attorney). No legal rule is introduced. The VAT option history records master data only, the tax treatment needs a released rule (S01, D45). Power of attorney: the signed document is mandatory, the access is read only and limited to the validity period (existing API rule), revoking takes effect at once |
| Acceptance case | None in annex D. Vitest per component (list, permission hiding, happy path, validation before the call, API refusal shown), API test `test_p13_portal.py` (representation list names the representative) |
| Implementation | Buttons only hide what the API refuses; permissions stay enforced by the API (`contacts:update`, `contacts:create`, `contacts:delete`, `properties:update`, `tickets:approve`, `tickets:update`, `tenant_settings:update`). Gallery: every change is one `PATCH /properties/{id}` with the complete `images` list and `If-Match`, a stale version shows a reload hint. Bulk assignment calls `POST /workspace/bulk` (`tickets.assign`), all or nothing, the user list is loaded when the assignment is opened. Ticket building select loads `GET /properties/{id}/buildings`, the API refuses a building of another property |
