# M12 Matching und KI-Kontierung: plan and result

Status: implemented without AI task (2026-09-23). Source: MASTER-PROMPT 6.9.4, 7.4, 18 (M12).
Acceptance: independent test set with wrong and ambiguous hits; error rate and coverage
reported separately; automation only per 7.4.

## Decisions

* `mhvp.banking.matching`: deterministic candidates (contract number in purpose, mandate
  reference, payer IBAN on file, full amount) with reasons; `unambiguous` requires more than
  IBAN plus amount and a full settlement of exactly one open item.
* Booking a bank transaction posts bank against debtor with explicit settlements (M10
  services); overpayment stays as credit on the debtor account; transfers need the partner
  bank account; booked or unresolved duplicates cannot be booked.
* `bank_rule` (migration 0012) with states proposed → approved (second person) → active (max
  amount and test evidence document) → disabled. Learning creates proposed rules only from
  confirmed bookings. Tenant opt-in `auto_posting_enabled` (default off, switch recorded).
* Bulk confirmation with preview (count, total, legal entities, exceptions); each transaction
  in its own savepoint (6.9.13).
* Metrics: coverage and error rate (reversed automatic bookings) separately.

## A45 (26.09.2026): Kennzahlen Abdeckungsgrad und Fehlerquote getrennt, je Zeitraum

* `mhvp.banking.matching_metrics.compute` and `GET /api/v1/banking/matching-metrics?from=&to=`
  (`accounting:read`, booking date window, `from > to` is rejected). The older
  `GET /matching/metrics` stays unchanged for existing clients.
* Coverage = transactions of the period assigned automatically and unambiguously and posted
  (`matched_rule_id` set) / all transactions of the period. Error rate = automatic assignments
  whose posting was reversed / automatic assignments; split into `auto_corrected` (a person
  posted the transaction again after the reversal, `journal_entry.bank_transaction_id`) and
  `auto_cancelled` (reversal only). Breakdown: `manual_booked`, `open` (new, needs review,
  proposed), `ignored`, `incoming`. Ratios as `NUMERIC` strings with four decimals, `null`
  without base. Computed from existing data only; the response carries the 7.4 note (no
  release of the automation).
* Web: `MatchingMetricsCard` on `/bank` with period selection (default: current month),
  component test `MatchingMetricsCard.test.tsx`.
* Test: `test_a45_matching_metrics_coverage_and_error_rate_per_period` in
  `tests/integration/test_m12_matching.py` with a synthetic March set: correct automatic hit,
  wrong automatic hit (payer quotes another contract, reviewer reverses), ambiguous purpose,
  IBAN plus amount only (manual), ignored transaction, one transaction outside the period.
  Expected values are precomputed (coverage 2 of 5, error rate 1 of 2).
* Open: after a reversal the bank transaction stays `booked` with the reversed entry, so a
  person cannot post it again through `/transactions/{id}/book`; `auto_corrected` therefore
  only counts entries posted through the accounting API with a bank transaction reference.
  A re-booking path after reversal is a separate task. The functional test set (M12-02)
  remains open.


## M12-03 Tilgungsbestimmung aus dem Verwendungszweck (D39, M10-03)

Stand 26.09.2026, umgesetzt.

- Modul `mhvp.banking.allocation`, Funktion `parse_allocation_hint(purpose)`: deterministisch, ohne KI. Erkennt Rechnungsnummern (Rechnung, Re.-Nr., RG-Nr.), Sollstellungsnummern (Sollstellung, Soll-Nr., SST-Nr.), Monate (09/2026, 9.2026, September 2026, Sept. 2026, auch ohne Jahr), Quartale (3. Quartal 2026, Q4/2026, als drei Monate) sowie Objekt- und Einheitskennungen (Obj., Objekt, WE, Wohnung, Einheit).
- Vor der Auswertung werden IBAN, SEPA-Felder (EREF, MREF, KREF, CRED) und Kalenderdaten entfernt, damit deren Ziffern nie als Nummer oder Zeitraum gelten.
- Zuordnung zum offenen Posten: Nummernhinweis gegen `journal_entry.reference` des Postens (ohne Leerzeichen, Bindestriche, Schrägstriche verglichen), Zeitraum gegen den Monat der Fälligkeit (ersatzweise Buchungsdatum).
- Matching (`matching.candidates`): Trifft ein Hinweis genau einen offenen Posten desselben Debitorenkontos, steht dieser Vorschlag zuerst, Grund `Bestimmung aus Verwendungszweck`; alle übrigen folgen in der bisherigen Reihenfolge (Punktzahl, Kennung) mit `Regel ohne Bestimmung`. Punktzahl und `unambiguous` bleiben unverändert, die automatische Buchung ändert sich nicht.
- `allocation_reason` erscheint im Vorschlag (`GET /transactions/{id}/candidates`), in der Vorschau der Massenbestätigung (`allocations` je Umsatz) und im Protokoll des Ereignisses `bank_transaction.booked` (`allocations`).
- Keine Migration, keine neue Abhängigkeit, OpenAPI unverändert (Antworten sind untypisierte Objekte).
- Tests: `tests/unit/test_banking_allocation.py` (21 Fälle inkl. Fehlerkennungen), D39 in `tests/integration/test_m12_matching.py` um Reihenfolge und Grund ergänzt.
- Offen: Objekt- und Einheitshinweise werden erkannt, aber noch nicht gegen Einheit oder Objekt des Postens geprüft; Bezeichnungen der Sollstellung außerhalb von `reference` werden nicht ausgewertet.
