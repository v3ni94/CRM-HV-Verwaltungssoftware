# M13 Sollstellung und Verwalterhonorar: plan and result

Status: implemented for monthly full month components; fee issued and rendered as XRechnung
(2026-09-26). Source: MASTER-PROMPT 6.4, 7.3, 7.5, 13.5, 18 (M13).
Acceptance: monthly run for all properties under 2 minutes (synthetic 67/869 portfolio passed 26.09.2026, real portfolio open, M13-05);
invoices valid as XRechnung (generation done, official validator passed locally, CI run and
tenant master data open, M13-04).

## Decisions

* `mhvp.accounting.receivables`, migration 0013: payment_type_account (revenue account per
  payment type and ledger), receivable_run (preview hash, totals), receivable_item (status
  ready, manual, blocked, posted, reversed; unique posted item per contract, component, month),
  admin_fee_setting.
* Preview computes items from contract payments and schedules; posting recomputes and refuses
  a stale preview; posting creates one receivable entry per item (debtor against revenue) with
  due date and idempotency key; reversal reverses all entries of the run.
* Proration, non monthly intervals, workday due rules, VAT and negative amounts are manual
  items (M13-01 to M13-03).
* Management fee: amounts per unit type, minimum and maximum, VAT rounding half up; result is
  a draft.
* 25.09.2026 (M13-04): `mhvp.platform.models.TenantBillingSettings` (migration 0069) holds the
  per tenant invoice prefix, VAT status (`unset`/`regelbesteuert`/`kleinunternehmer`), encrypted
  VAT ID and tax number (masked in the API to the last 4 characters), Leitweg-ID and the
  Kleinunternehmer note text; all nullable, nothing invented. `mhvp.accounting.numbering` holds
  `allocate_invoice_number`, allocating a gapless `PREFIX-JJJJ-000001` number under a locked
  `InvoiceNumberCounter` row (mirrors the journal counter, tested under concurrency). The
  Verwalterhonorar path (`POST /admin-fees/{id}/invoice-issue`) calls it and blocks with
  MHVP-BILL-0002/0003 when the VAT status or the tax data XRechnung needs is missing. The
  dunning fee invoice path is a separate agent's concurrent work; it is not wired here and gets
  its own call to `allocate_invoice_number`. `GET`/`PATCH /tenant/billing-settings` and a CRM
  section "Rechnungsstellung und Steuer" (Einstellungen/Mandant) let the operator enter the
  values. XRechnung XML generation and the official validator run (P05) are still open.

* 26.09.2026 (A12, D41): `mhvp.accounting.xrechnung` and `AdminFeeInvoice` (migration 0094,
  plus `tenant_billing_settings.payee_iban`, encrypted). `POST /admin-fees/{id}/invoice-issue`
  now persists the issued invoice (number, date, amounts, lines with explicit minimum or maximum
  adjustment, debtor) and returns its `id` and `xrechnung_url`. `GET
  /accounting/invoices/{id}/xrechnung.xml` renders UBL 2.1 with CustomizationID
  `urn:cen.eu:en16931:2017#compliant#urn:xeinkauf.de:kosit:xrechnung_3.0`; `GET
  .../xrechnung/check` returns structural findings (mandatory business terms, sums); `POST
  .../xrechnung/document` files the XML once, linked to the property and the community.
  Incoming invoices and drafts answer 409 (MHVP-BILL-0006). Missing Leitweg-ID (MHVP-BILL-0005),
  payee IBAN (MHVP-BILL-0007), tax data (MHVP-BILL-0002/0003) or company contact data lock the
  generation; nothing is defaulted. Three variants were accepted by the KoSIT validator 1.5.0
  with configuration xrechnung_3.0.2_2024-10-31 (run locally, `scripts/kosit_validate.sh`; the
  jar is not bundled and CI has no network access). Rule: `docs/rules/M13-04.md`.

* 26.09.2026 (A27, M13-05): runtime measured with a synthetic portfolio of 67 HOA properties
  and 869 units (one ownership contract each with hoa_fee 300,00 and reserve 50,00 monthly,
  schedule day 3, ledger from the default template, revenue mapping), built directly on the
  services in an own tenant (`_load_world` in `tests/integration/test_m13_receivables.py`,
  marker `slow`, run with `-m slow -s`). Measured on the API path on the development
  container (local PostgreSQL, 26.09.2026): 67 runs with scope=property for July 2026:
  preview 5,5 s, posting 33,5 s, total 39,1 s for 1.738 items; one run with scope=all for
  August 2026: preview 2,1 s, posting 27,2 s, total 29,2 s. Both are below the two minute
  limit of the acceptance, so `receivables.py` was not changed; the posting still runs one
  journal entry per item with the gapless number counter (B04), which is the dominant cost
  (about 16 ms per item) and the first place for batching if a real portfolio is slower.
  Portfolio build: about 6 s. A measurement with the imported HVM portfolio (M8-01) is still
  outstanding.
