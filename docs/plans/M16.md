# M16 Mahnwesen: plan and result

Status: preview, locks, approval, fee levels and Mahnbescheid preparation implemented
(2026-09-25); fee amounts and Basiszinssatz stay empty until the operator enters them, letters
(M16-02) still open.
Source: MASTER-PROMPT 6.4, 6.9.10, 7.5, 13.1, 15.1, 18 (M16).
Acceptance: dunning run for all properties with approval; dunning blocks respected;
delivery evidence (open, M16-02).

## Decisions

* `mhvp.accounting.dunning`, migration 0016: dunning_settings (levels: level, minimum days,
  text; threshold; tenant default with property override), dunning_run, dunning_case (level,
  items, total, fee and interest always 0,00, status proposed or excluded with reason).
* Only the leading system may dun (6.9.10, 13.1): cases in a comparison ledger are excluded;
  approval refuses non leading ledgers and requires a second person.
* Celery `mhvp.accounting.dunning_run` on the 5th at 06:00 creates previews only.
* Migrations 0068 (schema), 0071 and 0072 (both same day fixes: the new tables were missing
  the `created_by`/`updated_by` and `created_at`/`updated_at` `server_default` columns every
  `TimestampMixin` table needs; caught by the integration test, not by review) (25.09.2026, V7
  teilweise entschieden): `dunning_settings` gets
  `fee_from_level` (nullable), `interest_enabled`, `interest_base_rate` (Basiszinssatz, operator
  maintained, no value shipped), `interest_spread` (Aufschlag); each level in `levels` may carry
  a nullable `fee_amount`. `dunning_case` gets `fee_entry_id` and `fee_invoice_draft_id`. New
  tables `dunning_fee_invoice_draft` and `dunning_mahnbescheid_prep` (docs/rules/M16-01.md).
* `POST /dunning-settings/presets` loads the V7 ladder (Zahlungserinnerung 7 Tage, always free;
  1. Mahnung 14 Tage; 2. Mahnung 28 Tage; 3. Mahnung/letzte Mahnung 42 Tage) with
  `fee_from_level = 2` and every `fee_amount` left empty; an optional `interest_profile`
  (`verbraucher`/`unternehmer`) only fills `interest_spread` (5 or 9 Prozentpunkte, § 288 BGB),
  never `interest_base_rate`. `PUT /dunning-settings` refuses `interest_enabled=true` without a
  maintained `interest_base_rate`.
* A fee stays inactive (amount 0,00, nothing posted) unless both `fee_from_level` is reached and
  that level's `fee_amount` is set; no default amount is ever assumed (0.1.3). Interest is
  computed only as an informational Nebenforderung for the Mahnbescheid preparation
  (`interest_amount_for`, a generic day count approximation, not a legal certification, 0.2);
  it is never booked automatically.
* On approval, a configured fee becomes a draft receivable (Sollstellung, `EntryKind.DUNNING_FEE`,
  status `draft`) on the debtor's account inside the claim holder's ledger (WEG for Hausgeld,
  Vermieter/Eigentümer for rent, matching the existing ledger-per-legal-entity model, 6.9.1).
  When the claim holder's legal entity is not `LegalEntityKind.MANAGER` (Hausverwaltung Müller
  GmbH), a linked `dunning_fee_invoice_draft` records the draft HVM outgoing invoice to that
  claim holder; when the claim holder is HVM itself, only the receivable is created. Both stay
  drafts behind G1 and the existing four eyes release (posting the receivable uses the generic
  `POST /ledgers/{id}/entries/{id}/post` endpoint, which already enforces a second person).
* `POST /dunning-cases/{id}/mahnbescheid-vorbereitung` (only at the highest configured level)
  creates a `dunning_mahnbescheid_prep` record (Antragsteller legal entity, Antragsgegner
  snapshot, Hauptforderung, Nebenforderungen from the recorded fee/interest, Zustelladresse,
  internes Aktenzeichen), status `in_vorbereitung` plus a `hinweis` field naming the pending
  review by a lawyer ("Vorbereitung, Prüfung durch Rechtsanwalt", moved out of `status` because
  that column is a short code field); `GET` returns the same export data. No PDF export yet
  (open point below); no filing, no legal claim of completeness, deadline hints are not
  computed here.

## Result

`alembic upgrade head` (single head, revision 0072) and
`tests/integration/test_m16_dunning.py` both run and pass (2 passed): locks/preview/approval
(unchanged behaviour), plus presets, fee posting with the draft receivable and the draft HVM
outgoing invoice for a non-HVM claim holder (WEG), and Mahnbescheid preparation including
repeat-safe `GET`. `tests/integration/test_m13_receivables.py` and
`tests/integration/test_m14_invoices.py` re-run green to check for regressions in adjacent
accounting code.

## Open points

M16-01 to M16-03 (updated), assumption A-029, plus:

* M16-06: no CRM UI yet for dunning settings (Vorschlagswerte laden, fee/interest fields) or
  for the Mahnbescheid action/download on the debtor's dunning history; backend only.
* M16-07: no PDF export for the Mahnbescheid preparation; only the JSON data set via
  `GET /dunning-cases/{id}/mahnbescheid-vorbereitung`.
* M16-08: the "own receivable" branch (claim holder is HVM itself, `LegalEntityKind.MANAGER`)
  is covered by the test only by inserting HVM's `LegalEntity`/`Ledger` directly in the test
  setup (`_seed_manager_ledger`), because no HTTP endpoint creates a `MANAGER` legal entity yet
  (only HOA/RENTAL_OWNER/SEV_OWNER are created through the property flow today). A rent/tenant
  case (contract kind `tenancy`) was not covered by a dedicated test either; the code path is
  the same as for the WEG case (fee posted at the debtor's account inside the claim holder's
  ledger). Creating HVM's own legal entity/ledger through the platform (a one-off operator
  setup step) is a separate, small follow-up.
* M16-09: dunning levels can only ever reach the level after the previous one was marked
  "sent" (`DunningCase.status == "sent"`); nothing in the platform sets that status yet
  (letters and delivery are M16-02, still open), so in practice every preview today proposes
  level 1. The fee test therefore uses a single-level ladder to reach a fee on the first,
  reachable level; testing the full multi-level ladder (fee starting at the 1. Mahnung, level
  2) needs M16-02 first.

## Betreiberentscheidung 25.09.2026 (V7, teilweise)

Stufenleiter und Ablauf sind entschieden (siehe docs/OPEN_QUESTIONS.md V7): Erinnerung
kostenlos, Gebühr ab 1. Mahnung ohne festgelegten Betrag, Verzugszins nach gesetzlicher Regel
mit vom Betreiber gepflegtem Basiszinssatz, automatische Entwürfe mit Freigabe, Gebühren als
Sollstellung und HVM-Rechnung, danach Vorbereitung Mahnbescheid. Klarstellung 25.09.2026: die
Gebühr wird als Sollstellung auf dem Debitorenkonto des Schuldners innerhalb des Buchungskreises
des Forderungsinhabers gebucht (bei Hausgeld: Forderungsinhaber die WEG, Schuldner der
Eigentümer; bei Miete: Forderungsinhaber der Vermieter/Eigentümer, Schuldner der Mieter); die
HVM-Rechnung über die Gebühr geht an den Forderungsinhaber (WEG bzw. Vermieter/Eigentümer), da
dieser die Gebühr bei seinem Schuldner einzieht und an die HVM zahlt. Umsetzung: Vorschlagswerte,
Gebühren- und Zinslogik nur mit gepflegten Werten, alles hinter G1 und Vier-Augen-Freigabe.
