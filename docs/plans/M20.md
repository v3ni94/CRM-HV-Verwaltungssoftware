## Freigabe und Versand (2026-09-24)

* `Message` (direction `out`) trägt neben `draft`, `pending`, `sent` jetzt `submitted_by`,
  `submitted_at`, `approved_by`, `approved_at`, `rejection_note` und `gmail_message_id`
  (Migration `0039`).
* Ablauf: ein Entwurf (`POST /mail/messages/{id}/reply-draft`, optional mit vorbelegtem
  `body`) lässt sich bearbeiten (`PATCH /mail/messages/{id}/draft`, nur `status=draft`), dann
  einreichen (`POST /mail/messages/{id}/submit`, `draft` -> `pending`). Freigabe
  (`POST /mail/messages/{id}/approve`, Berechtigung `communication:approve`) verlangt das
  Vier-Augen-Prinzip: `principal.user_id` darf weder `created_by` noch `submitted_by` sein,
  sonst `409`. Bei Erfolg wird gesendet (Gmail über `gmail.GmailClient.send_raw`, sonst der
  bestehende SMTP-Weg), `status` wird `sent`, `header_message_id` kommt aus der erzeugten Mail
  (`email.utils.make_msgid`), bei Gmail zusätzlich `gmail_message_id`; am verknüpften Ticket
  entsteht ein `TicketEvent` `mail_sent`, das Ereignis `mail.sent` wird ausgelöst. Schlägt der
  Versand fehl (z. B. `403` von Gmail, fehlende Sendeberechtigung), bleibt der Status `pending`
  und die Anfrage endet mit `409`. `POST /mail/messages/{id}/reject` (`communication:approve`,
  Pflichtfeld `note`) setzt `pending` zurück auf `draft` mit `rejection_note`.
* Der frühere `POST /mail/messages/{id}/send` (ohne Freigabe) ist entfernt.
* `GET /mail/messages` filtert zusätzlich nach `direction`, `ticket_id`, `mailbox_id` und `q`
  (Volltext auf Betreff, Absender, Text). `GET /mail/messages/{id}` liefert eine einzelne
  Nachricht, `GET /mail/messages/{id}/thread` alle Nachrichten desselben `thread_id`
  chronologisch nach Eingang, Versand oder Anlage.
* Gmail-Scope erweitert um `gmail.send` (`gmail.SCOPES`). Bestehende Gmail-Postfächer müssen
  deshalb einmal erneut über "Mit Google verbinden" autorisiert werden, sonst schlägt der
  Versand mit `403` fehl.
* Berechtigung `communication:approve` ist Teil von `ALL_PERMISSIONS` und damit automatisch bei
  den Administratorrollen; sie ist bewusst in keiner Sachbearbeiterrolle enthalten und wird pro
  Mandant über eine eigene Rolle vergeben (`POST /roles`).
* Tests: `tests/integration/test_m20_mail_approval.py` (Entwurf bearbeiten, submit, Freigabe
  durch denselben Nutzer scheitert, Freigabe durch einen anderen Nutzer sendet über die
  gefälschte Gmail-API und legt das Ticket-Event an, reject, `403` von Gmail führt zu `pending`
  und `409`, Filter, Thread).

* Package `mhvp.communication`, migration 0019: mailbox (credentials encrypted), message.
* Intake from `.eml` documents: sender matched to contact e-mail, property number, urgency and
  template category by rules, dates as appointment suggestions, attachments stored, threading
  by Message-ID and In-Reply-To, re-import without second case.
* Ticket from mail (source e-mail, SLA), reply draft from a template, sending only with an
  enabled mailbox; appointment suggestion into the calendar on request.
* Gmail sync (M20-01, 2026-09-25): `gmail.py` (read only client: token refresh, history cursor,
  raw messages), `services.py` (intake shared with the .eml upload), `tasks.py` (Celery
  `mhvp.communication.gmail_sync_all`, every 60 s (safety net next to the Pub/Sub push, previously 300 s), Redis lock against overlap, queue `mail`, one transaction per mailbox).
  Endpoints: `GET /mail/mailboxes`, `PATCH /mail/mailboxes/{id}` (refresh token, enabled),
  `POST /mail/mailboxes/{id}/sync`. Migration 0035 (`gmail_history_id`, `last_synced_at`,
  `last_error`). Settings `MHVP_GOOGLE_CLIENT_ID`, `MHVP_GOOGLE_CLIENT_SECRET`,
  `MHVP_GMAIL_SYNC_BATCH`.
* Rules (docs/integrations/mail-optimierung.md, decided 2026-09-25): every inbound mail creates a
  ticket; a reply inside a known thread (In-Reply-To) attaches to that thread's ticket and writes
  a `mail_received` ticket event; the same Message-ID is never ingested twice; an expired Gmail
  history (404) restarts from the inbox and relies on that deduplication. Manual `.eml` upload
  keeps `auto_ticket=false` by default.
* Mailbox settings page (2026-09-25, `/einstellungen/postfaecher`, permission
  `tenant_settings:update`): the tenant stores its own Google OAuth client (`PUT
  /mail/oauth/google`, secret encrypted in `tenant_settings`, environment variables remain the
  fallback); "Mit Google verbinden" (`POST /mail/oauth/google/start`) opens the Google consent
  screen, the unauthenticated callback (`GET /mail/oauth/google/callback`, state in Redis, 10
  minutes, single use) exchanges the code and creates or refreshes the Gmail mailbox (address
  from the Gmail profile, refresh token encrypted, enabled). Access: a mailbox marked
  `is_default` is visible to every member including new ones; other mailboxes only to users
  granted via `PUT /mail/mailboxes/{id}/users` (`mailbox_user`); holders of
  `tenant_settings:update` see everything; `GET /mail/messages` applies that filter. Removing a
  mailbox keeps its messages and tickets. Migration `0036`.
* Operator setup for M20-01: in the Google Cloud Console create an OAuth client of type web
  application with the redirect URI shown on the settings page
  (`{MHVP_API_PUBLIC_URL}/api/v1/mail/oauth/google/callback`), enable the Gmail API, enter
  client id and secret on the page, click "Mit Google verbinden" as `info@muellerhv.de` and
  mark the mailbox as default. `MHVP_WEB_CRM_URL` makes the callback redirect back to the page.
* Tests: `tests/integration/test_m20_mail.py`, `tests/integration/test_m20_gmail.py` (fake
  Gmail API via httpx MockTransport, OAuth flow, access and default mailbox). Open: M20-01
  operator part (consent for info@), M20-02.

  Nachricht vor (Verweis aus dem Ticket).
