## Decisions

* Package `mhvp.billing`, migration 0017: statement (status model 6.9.3, versions with
  supersedes), statement_cost_item (amount, key or external amounts per occupant, basis,
  heating flag), statement_snapshot (inputs, results, rule version, hash), statement_event.
* Occupancy per unit from tenancies; vacancy periods stay with the owner (A05).
* Distribution by key value times days (A-030); heating only from external amounts (H01);
  rest cents per D08.
* Advances due and paid per tenant from posted receivable items and settlements (A04).
* Deadline orientation and access date; late claims block issuing without exception.
* Internal approval by a second person; issuing requires G3; changes after calculation only
  as new version; issued snapshot stays unchanged (A01).
* CO₂ helper for residential buildings (D10), registered as rule H04, not released.

* A23 and A24 (26.09.2026, annex D cases D21, D22, D23, D28):
  * D21: in a SEV ledger the statement covers only the units the owner held in the period
    (`services.occupants`, legal entity separation 6.9.1). A key copied from the tenant
    template (living area) is refused for a let condominium; the key must be recorded for the
    property and its source (declaration of division, deviating lease clause) is documented
    in the position basis (§ 556a Abs. 3 BGB, A03). Key facts (code, name, template flag) go
    into the snapshot positions. No key source field exists on `allocation_key`; a separate
    field is not introduced without the cost type schema of M17-01.
  * D22: a position with an account is accepted only when the account is classified as
    allocable (`ledger_account.allocation_category`); "none" (account name is no proof) and
    "non_allocable_*" are refused. The amount must not exceed the costs posted on that account
    in the period, so the split of a mixed invoice is proven by the posting. Positions without
    an account stay possible with their contractual basis (existing behaviour).
  * D23: issuing checks the access day against the calculation day of the snapshot (creation
    is never access) and against the deadline orientation: an additional payment whose access
    lies after the deadline is refused without a recorded exception (`services.check_issue`).
    The calculation day no longer decides alone (`late_claim_blocked` stays as pre check).
  * D28: `calc.RULE_VERSIONS` selects the rule version by period start (A-045);
    `statement_snapshot.rule_version` keeps the version used, later versions never touch old
    statements, also not through a new version of the same statement.

* Owner statement (A06, task A25, 26.09.2026): `mhvp.billing.owner_statement` with table
  `owner_statement` (migration 0097), pure `build_results` on plain inputs, `collect_inputs`
  from the posted ledger of the `rental_owner` or `sev_owner` entity; blocks income (rents and
  advances apart), expenses, management fee only from `admin_fee_setting`, payouts, open rent
  receivables, deposits (never liquidity), free liquidity, SEV reconciliation from the WEG
  individual statement (`mhvp.hoa`); sum checks as findings; status draft, calculated,
  internally_approved (second person); PDF behind G3 (403 MHVP-GATE-0001). Endpoints
  `/api/v1/billing/owner-statements`; CRM page Buchhaltung, Eigentümerabrechnung. Rule
  `docs/rules/A06-owner-statement.md`.

## A35 KI-Plausibilität (26.09.2026)

* Task `check_statement` (9.2, tier `large`, prompt `mhvp/ai/prompts/check_statement/v1.md`,
  schema `CheckStatementResult` in `mhvp/ai/tasks.py`): findings with field, description,
  severity (low, medium, high), reference to a position (P1, P2, ...) or a unit, plus an
  overall assessment and a short summary. No amount, no correction, no decision (rule 0.1.6).
* Input (`mhvp/billing/ai_check.py`, deterministic): positions with amount, key facts and
  account facts from the snapshot (`services.check_item`), result per unit, totals, posted
  account balances, previous period where the ledger holds a calculated statement ending the
  day before this period (change in percent computed by the platform). Masked: contract and
  unit ids dropped, parties as unit numbers, IBAN, e-mail, phone and titled names in free
  text replaced (`mask_free_text`); `assert_masked` refuses a payload with an id or IBAN.
* Endpoints (`mhvp/billing/ai_check_routers.py`): `POST` and `GET`
  `/statements/{id}/ai-check` (M17) and `/hoa/statements/{id}/ai-check` (M24). The run goes
  through the gateway (release, DPA evidence, budget, deduplication by input hash); the result
  is an `AiProposal` of entity type `statement_check` (`mhvp/ai/jobs.py`). The snapshot hash
  is recorded in the proposal; the statement, its snapshot and its status stay untouched.
  `normalize_result` orders and deduplicates the findings, clears references to unknown
  positions or units and derives the overall assessment from the highest severity instead of
  the model's own word.
* CRM: card "KI-Plausibilität" (`AiPlausibilityCard`) on the operating cost statement and the
  HOA statement page; the button is disabled without a snapshot, a proposal for an older
  snapshot is marked.
* Evaluation: `tests/ai_eval/check_statement/cases.jsonl`, 24 fictitious recorded cases
  (previous year deviation over 30 percent, key without source, position without account,
  implausible totals and advances, reserve, negative cases without findings, duplicates and
  unknown references); scorer `_check_statement` in `mhvp/ai/evaluate.py`, F1 1.0.
* Tests: `tests/unit/test_m17_ai_check.py` (input assembly, masking, change percent,
  normalisation, schema, offline evaluation), `tests/integration/test_m17_ai_check.py`
  (fake provider: happy path, rights, tenant separation, no change to the snapshot, masked
  prompt content, deduplication, refusal without snapshot).
* Open: the HOA path is implemented and typed but has no integration test yet (the M24 world
  setup is large; unit test covers `build_hoa_input`). Names without a title in a cost label
  or basis are not masked (heuristic, like `mhvp.objektakte.masking`). `apps/api/openapi.json`
  and the generated client were not regenerated in this task (parallel work on the file);
  the card uses the BFF, not the typed client. A live run needs M7-01.

## A34 (26.09.2026): Anschreiben Guthaben/Nachzahlung je Mieter (7.6 A07)

* `mhvp/billing/letters.py`: one letter per tenant from `statement_snapshot.results` only
  (costs, advances due and paid, balance, result kind); advance proposal = costs of the
  period / 12, rounded half up, labelled as a proposal (no formula in the master prompt;
  `docs/rules/A07-tenant-letters.md`); no proposal for a tenancy that ended in the period;
  hint for a tenancy that started in the period. Letterhead via `mhvp.documents.letters`
  (DIN 5008, company data of the tenant). No AI text.
* `mhvp/billing/letter_routers.py` (registered in `main.py`, prefix `/statements`, next to
  the existing statement router; the task named `/billing/statements`, the existing statement
  routes live under `/statements`): `POST /statements/{id}/letters/preview` (single PDF with
  `contract_id`, else bundled PDF via pypdf), `POST /statements/{id}/letters` (draft documents
  per tenant, source `generated`, links contract, unit, property, contact; response with the
  snapshot values and hints such as `late_claim_blocked`), `POST /statements/{id}/letters/send`
  (G3 gate, then always 409: dispatch and proof of access not released, M17-04).
* Test `test_m17_operating_costs.py::test_a07_tenant_letters_from_snapshot` (own S3 mock
  fixture `letter_clients`, hand computed values in the docstring): PDF text contains
  result and proposal, bundled PDF in unit order, filing with links, 409 without snapshot,
  403 with G3 closed and 409 with G3 open, foreign tenant 404.
* Open: formula of the proposal, Informationsblatt and § 35a Nachweis (M17-05), dispatch and
  access (M17-04), no CRM screen for the letters yet (API only), `openapi.json` and the
  generated client not regenerated in this task.
