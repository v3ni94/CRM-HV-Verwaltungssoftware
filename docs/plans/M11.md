# M11 Bank-Adapter: plan and result

Status: implemented for file import (CAMT.053 and MT940 since 26.09.2026), connectors pending contracts. Source:
MASTER-PROMPT 6.4, 6.9.7, 8, 18 (M11).
Acceptance: agreed HVM accounts connected (open, M11-01); re-import without additional effect
and two real identical payments kept (done, D05); bank reconciliation and sync protocol (done).

## Decisions

* Package `mhvp.banking`, migration 0011: bank_connection (credentials encrypted, never
  returned), bank_sync_run (protocol), bank_statement (balances), bank_transaction
  (bank reference unique per account, content hash as duplicate hint, transfer pair,
  counterpart IBAN encrypted with fingerprint).
* CAMT.053 parser with defusedxml, namespace agnostic; accounts matched by IBAN fingerprint to
  own bank accounts of a legal entity (B01); unknown IBAN is refused.
* Internal transfers are paired (D04), not booked; posting follows in M12.
* Reconciliation per statement (opening + movements = closing) and against the linked ledger
  account; differences are shown, never booked away (B09).
* `mhvp.banking.sync_all` daily 06:00; connectors without contract report "not configured";
  consent reminder 10 days before expiry.
* No payment initiation (G2).
* 26.09.2026 (A28, M11-02): MT940 on the same file path. `mhvp.banking.mt940` parses only the
  public SWIFT field structure (`:20:`, `:21:`, `:25:`, `:28C:`, `:60F:`/`:60M:`, `:61:`,
  `:86:`, `:62F:`/`:62M:`), several statements per file (plain or in `{4:` ... `-}` blocks),
  amounts with comma, D/C and reversals RC/RD, value and entry date (entry date without year
  is placed by the value date and corrected at the turn of the year), transaction type code,
  customer reference and `//` bank reference. `:86:` is always kept as raw text
  (`raw.info.info_raw`); the German subfield layout (`GVC?00...?34`: `?20` to `?29` and `?60`
  to `?63` purpose, `?30`/`?31` bank and account of the counterpart, `?32`/`?33` name) and the
  SEPA prefixes (`EREF+`, `MREF+`, `CRED+`, `SVWZ+`) are read only when the text matches that
  pattern and are marked `convention: dk_subfields`; anything else stays raw text. Both parsers
  yield the same `ParsedFile`, so `services.import_file` normalises MT940 exactly like CAMT
  (bank reference primary, content hash secondary, D05, review without reference). Without a
  `//` bank reference the transaction gets a deterministic reference from statement number,
  line number and value date (`raw.reference_source = derived:28C/line/value_date`, A-046) so
  that a re-import of the same file has no additional effect. `FileConnector.parse` chooses
  the parser by suffix (`.sta`, `.mt940`, `.940`, `.swi`) or content (`:20:` at the start);
  `POST /banking/imports` uses it for every upload. `:25:` in the form BLZ/Konto is not an
  IBAN and is refused by the account matching like any unknown account. Bank specific CSV and
  the Immoware24 export remain open (M11-02, B14).
