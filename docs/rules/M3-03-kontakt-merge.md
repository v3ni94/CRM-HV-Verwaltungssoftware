# M3-03 Kontakt zusammenführen

| Field | Content |
| --- | --- |
| ID | `M3-03` |
| Title | Merge of two contacts as a proposal with check, four eyes execution and audit, no deletion |
| Scope | `mhvp.contacts.merge`, `mhvp.contacts.routers_merge` (`GET/POST /contact-merges`, `GET /contact-merges/{id}`, `POST /contact-merges/{id}/reject`, `POST /contact-merges/{id}/execute`), table `contact_merge`, columns `contact.merged_into_id` and `contact.merged_at` (migration 0273); CRM `/kontakte/zusammenfuehrung` |
| Source status | Fachliche Umsetzung and Produktschutz. No legal rule is introduced. Data protection aspects (retention of the merged source) follow the existing deletion path and the erasure request, nothing is deleted by the merge (rule 7). Open question P16-01 stays open for the final decision of the operator |
| Acceptance case | None in annex D. Tests `apps/api/tests/integration/test_contact_merge.py` (references move, four eyes, blockers, permissions, 422, other tenant 404, registry covers every foreign key to `contact.id`, search routes the old name to the target), Vitest `ContactMergeAdmin.test.tsx` |
| Implementation | Registry of references: every foreign key to `contact.id` found in the SQLAlchemy metadata (child tables of the contact, parties, contracts, tickets, invoices, portal, communication and more), plus the polymorphic link `document_link` (`entity_type = contact`). Excluded: `contact_merge` and `privacy_erasure_request` (history stays on the source). Each row is re-pointed in its own savepoint; a row that would break a unique constraint on the target (for example the same tag) stays on the source and is reported as a conflict. Check blockers: same contact, source or target deleted, merged or anonymised, different kind (person or company), open erasure request, bank accounts of the source in pending release. Warnings: different birth date, different block flag, different display name. Execution needs a second person than the proposer and `contacts:approve`, repeats the check and stops at any blocker. After the merge: empty scalar fields of the target are filled from the source (salutation, letter salutation, title, legal form, position, date of birth, preferred channel, consumer flag), roles are united, external ids are united (target wins), the search text of the target takes the tokens of the source (old name stays findable). The source row is marked (`merged_into_id`, `merged_at`) and hidden (`deleted_at`), it is not deleted. Bank accounts keep their approval status, no IBAN is approved by the merge. Audit events `contact.merge_proposed`, `contact.merged`, `contact.merge_rejected` |
